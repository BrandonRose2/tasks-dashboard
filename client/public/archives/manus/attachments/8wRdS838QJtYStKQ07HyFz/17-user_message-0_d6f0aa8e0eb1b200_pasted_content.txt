1. What Robert Asked For

The recording describes a private weekly NFL pick’em pool with roughly 200 friends. Each person can buy one or more $10 entry cards, pick the winner of each game, enter a predicted combined Monday Night Football score as a tiebreaker, and later see results through a shared leaderboard. Robert wants the portal to eliminate the existing workflow of sending a flyer, tracking person-to-person payments, retyping picks into Excel, manually checking results, and distributing weekly spreadsheets. 

The portal should be a mobile-first website, rather than a native app, because a friend should be able to tap a secure link in a text message, enter the private group, and make picks immediately. The same site can later be saved to a phone’s home screen and behave much like an app without an App Store installation.

2. The Core Experience

Player flow

A user opens the texted link and verifies their identity using either email magic link or phone-based sign-in. For a private group, I would begin with an invite-only roster: Robert imports names and phone numbers, and only invited people can create an account. This prevents strangers from accessing the group merely because a link was forwarded.

The player then chooses the current NFL week, selects the number of cards, and completes the payment step selected by the legally approved operating model. Each card displays the week’s games, lets the player tap one winner per matchup, and asks for the combined Monday Night Football score. The player reviews and submits. The portal records the exact submission time and locks that version.


Fairness rule: players may edit an unsubmitted draft, but a submitted card should not change after the cut-off. If edits before the deadline are permitted, each saved revision should be retained in an audit log. To prevent copying, other players’ picks should be hidden until the deadline; each person can always see their own cards.

The MVP should not initially include public leaderboards, social feeds, sports betting odds, cash-out functionality, unlimited open registration, or automatic prize payouts. Those features add risk and complexity without solving the main operational bottleneck.

4. Payment: Use a Deliberate Two-Step Design

Robert mentioned Zelle, Cash App, Venmo, and a desire to authenticate entries against payment. In practice, the portal needs to distinguish submitting a pick card from confirming payment.

The portal should never treat a card as fully eligible merely because a participant clicked “paid.” The status should remain Pending verification until Robert or an approved payment event confirms it. The system can allow a participant to make picks while pending, but a card must be in Verified or Waived status before the deadline to be eligible.

If Robert has free cards or internal organizer adjustments, those should be created through a visible admin action with a reason field. Any organizer fee or prize allocation should be calculated transparently in an internal contest ledger, but it should not be exposed as a general payment feature until it has been legally reviewed.

7. Technical Blueprint

This should be built as a secure full-stack web application with a responsive interface, an authenticated database, an administrator role, and scheduled background tasks. It does not need a persistent always-on server for its normal workload: scheduled reminders and score refreshes can run in the background on a managed application host.

The database should treat every submitted pick card as an immutable contest record. Important entities include Member, Invitation, ContestWeek, Game, EntryCard, CardPick, PaymentRecord, Result, NotificationConsent, Notification, and AuditEvent. That structure lets Robert correct a legitimate error without erasing what originally happened.

8. Text Sharing and Reminder Design

The initial text link should be simple, identifiable, and safe to forward only within the intended group. Example:


Robert’s NFL Picks — Week 4 is open. Submit your card before Saturday, 11:59 p.m. CT: https://[short-link]
Reply STOP to stop reminder texts.

For automated texts, the portal must record affirmative consent, identify the sender, provide a simple opt-out mechanism, and stop reminders for opted-out recipients. The FCC states that autodialed texts to a mobile phone require prior consent and that recipients may opt out of robotexts in a reasonable manner.

9. Build Sequence

Work package 1 — Product and compliance foundations

Finalize contest rules, legal review scope, payment method, message-consent language, privacy policy, age/geography eligibility, deadline timezone, pick reveal policy, tiebreak rules, and prize-handling process. This work package ends with a signed-off functional specification and clickable screen map.

Work package 2 — Private portal MVP

Build the player experience and Robert’s admin console: private invites, sign-in, weekly cards, pick submission, payment-status queue, manual results entry, scoring, weekly/season leaderboard, exports, and audit log. Test all deadline, multiple-card, tiebreak, and admin-exception cases before inviting the full group.

Work package 3 — Pilot with a small trusted group

Run one complete private test week with a small group. Confirm the phone experience, accepted payment workflow, contest locking, result scoring, message language, and records. Use real test data but do not accept live paid entries until the legal/payment workflow is approved.

Work package 4 — Production rollout

Import the 200-person roster, send opt-in invitations, set up the live weekly schedule process, run the first public-to-the-group week, and retain a manual fallback spreadsheet for the first few live cycles. After the workflow is stable, add approved score-data automation and compliant payment automation only if they are still worthwhile.

10. Questions to Resolve Before Coding

1.
What state or country governs the group, and will all participants be adults located in the same jurisdiction?

2.
Is Robert willing to keep payments manual at launch, with the portal simply tracking and verifying them, or does he want to wait for an approved integrated-payment design?

3.
Should everyone see all picks only after the deadline, or immediately after their own card is submitted?

4.
Is the contest always all NFL games that week, including Thursday and international games, or does it begin with Sunday games only?

5.
What should happen if two entrants also have the exact same Monday-night combined-score prediction?

6.
Does Robert want one private pool initially, or the ability to create separate groups for different circles of friends later?

7.
Does he already have the prototype link/screens he showed in the recording? If so, those can be used as a design reference rather than rebuilt from memory.

Bottom Line

This is very feasible as a private, text-shareable web portal. The core product is not a complex betting platform; it is a secure weekly contest-management system that handles membership, cards, picks, deadlines, payment-status verification, scoring, standings, and reminders. The most important design choices are: keep the first release mobile-first and invite-only; lock/audit submitted picks; hide group picks until the fair reveal point; use a payment-verification queue at launch; and complete jurisdiction-specific legal and payment review before money moves through the portal.
