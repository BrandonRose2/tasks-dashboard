1. Know what is in the package

Verified export: 226 application files; 17 database tables with 8,500 rows; nine configured application credential values and seven source-account recovery dependencies inside the encrypted archive; one backed-up public logo. The packaged application passed 795 tests, with seven live-gated tests skipped, plus TypeScript and production build checks.

Keep the package together. Use manifest.json as the authoritative inventory, including any available integrity hashes and export notes. These documents describe the intended handoff layout; they do not independently certify every exported file or credential.

  • application/

    Application source from checkpoint 48233d76, preserved byte-for-byte. Known credential values were checked and not found in these source files. The seven root support files are parser test fixtures and retired/non-sending guards, not production send commands. Configure the corresponding environment variables in the destination; do not put secrets back into source files.

  • configuration/report-configuration.json

    The exported report settings and actual recipients. Use this file rather than guessing anyone’s email address from the names below.

  • configuration/source-heartbeats-reference.json

    Reference information for the original external jobs. Source unique IDs (UIDs) identify source-owned jobs only; they are not destination bindings.

  • configuration/destination-heartbeats-disabled.json

    A disabled destination template. Create destination-owned jobs and bind their new UIDs before considering activation.

  • configuration/credential-inventory.json

    Credential names, export status, and classification only—not password or token values. Review missing, unavailable, expired, and account-bound dependencies.

  • PRIVATE_DATA_AND_CREDENTIALS.zip

    AES-256-encrypted archive containing the confidential database snapshot and exported credentials. The unlock key is delivered separately, not in these guides.

  • tools/unlock_private.py

    Optional Python decryption helper. A technician can review its instructions and dependencies; the GUI archive route below is preferred.

  • manifest.json

    The package inventory and recorded export details. Review the package’s asset inventory as well. The public logo is backed up at assets/asset_1.png. This is not a complete export of all hosted/private assets; see configuration/asset-inventory.json.

Inside the encrypted private archive
  • credentials/application-secrets.json and credentials/transfer.env

2. Open the private archive safely

  1. Save a private working copy

    Use a device and private folder approved for company data. Keep the original archive intact. Do not upload the archive or decrypted database to public links, shared repositories, public web folders, or online ZIP-unlock services.

  2. Receive the key separately

    Obtain the unlock key through the separately agreed secure channel. Do not place it beside the ZIP, forward it in the same message, or expose it in screenshots, tickets, or logs.

  3. Use an AES-capable archive app

    Open the ZIP in a trusted third-party tool that supports AES-encrypted ZIP files, such as 7-Zip on Windows. Choose Extract in its interface and enter the separate key when prompted. A default operating-system extractor may not support this encryption; an unsupported-format message is not proof the archive is damaged.

  4. Limit access to decrypted files

    Extract only to a restricted private folder. Share values only with an authorized technician through an approved secrets manager or destination secret-settings interface. Never publish transfer.env or the private archive contents as application assets.

No password or token values are displayed in this guide. The optional Python helper is for a technician; no terminal instructions are required to read or use this handoff.

3. Prepare the new owner’s destination

The recipient needs a separately owned project or hosting environment. Source code portability does not automatically recreate the database, account permissions, hosted services, email authorization, assets, domains, or scheduler bindings.

  1. Confirm authority and ownership

    Confirm permission to transfer the application, confidential records, and each third-party integration. Establish the new owner’s admin identity and test access. Do not assume the source owner’s login or imported user roles make the new owner an administrator.

  2. Create destination infrastructure

    Have a technician use the destination platform’s supported interface to set up the React frontend, Express backend, database, and authentication. Create the destination’s own database connection, platform keys, storage access, and scheduler ownership. Use the application’s documentation for build and runtime requirements.

  3. Configure secrets—not source credentials blindly

    Review both credential inventories. Regenerate platform and account-bound credentials in the destination. Reauthorize third-party services; reuse an exported user-configured credential only when permitted and still valid. Keep all values in destination secret settings, not source control or browser-visible code.

  4. Import data with sending blocked

    Review the schema, restore business data, preserve historical ledgers, and reconcile table counts and relationships against the private table manifest. Use disabled destination schedule seeds. Keep every destination job disabled and block outbound production email, including manual sends, during validation.

  5. Replace URLs and validate assets

    Update the public dashboard URL and every environment-specific asset URL. Check branding, logo, images, exports, report links, and access permissions. Stable preview assets were tested in the original environment; this is not proof they will work in the destination. Resolve any missing or inaccessible assets listed in the inventory before sign-off.

5. A controlled cutover comes later

This export is a point-in-time snapshot, not the final cutover state. New data, schedule changes, and sends can occur after capture while the current system remains active. A future cutover must be coordinated with the source owner.

  1. Validate in isolation

    Keep source production unchanged while destination jobs and production outbound email remain disabled. Test previews and calculations without sending. If email testing is approved, use a controlled test mailbox and explicit recipient overrides; do not trigger live report lists.

  2. Agree on a cutover window

    Record who authorizes the switch, the final source reporting period, pending sends, and rollback ownership. Arrange a short freeze or reviewed reconciliation of source writes so the final snapshot remains consistent through activation.

  3. Stop all old sending paths first

    During the approved window, disable the four source external jobs and any manual or alternate production-send paths. Confirm pending sends have finished or are explicitly reconciled. Do not enable the destination merely because a source database row was marked inactive.

  4. Take and reconcile a final fresh snapshot

    After source senders are stopped and in-flight work is resolved, capture a fresh database/configuration snapshot and reconcile changes since this package. Preserve sending history and report-period identifiers. Do not reset sent, sending, or unknown states to force a resend; investigate uncertain outcomes before any retry.

  5. Enable only after explicit sign-off

    Confirm new UIDs, ownership, time zones, recipients, URLs, sender authorization, and duplicate-send protections. Enable destination jobs only when the old senders are confirmed stopped. Monitor the first production cycle and reconcile its delivery status.

Never run both production senders at once.
If rollback is needed, stop destination sends first and reconcile its delivery history before re-enabling the source. Do not replay uncertain or already sent periods automatically.

6. Owner and technician sign-off

Use this as a review checklist, not evidence that the transfer has happened.

  • Package contents and any supplied hashes match the manifest; snapshot time and export limitations are understood.
  • The new owner can sign in as the correct administrator; unauthorized access is denied.
  • Destination secrets are configured privately; source-bound platform credentials have been replaced or reauthorized appropriately.
  • Business data, table counts, relationships, and historical sending ledgers reconcile; source active-job flags and UIDs were not imported as live destination bindings.
  • Dashboard URL, asset URLs, logos, permissions, report previews, and export/download behavior work in the destination.
  • All five report types match approved recipients, routing, time zones, and reporting periods; controlled tests have not sent to production lists.
  • Four destination-owned jobs have new UIDs and remain disabled until the approved cutover.
  • Before activation: old senders are stopped, the final fresh snapshot is reconciled, uncertain send states are resolved, and rollback responsibility is documented.
  • After verified handoff: rotate reusable credentials as appropriate and remove temporary decrypted copies according to company retention policy.
Technician appendix · implementation boundaries

This is an existing React/Express/Drizzle application, not a static-site deployment. Review the exported source documentation and dependency files before choosing the supported build, runtime, and schema-import process. The provided files do not promise a universal importer or automatic deployment script.

Review tools/unlock_private.py before using it. It is an optional decryption route, not a migration or deployment tool. Keep the separate key out of logs and recorded command arguments.

Treat database/schema.sql as the exported schema and the JSON table files as the exact snapshot. Adapt a migration to the destination database and verify IDs, types, foreign-key relationships, timestamps, and report ledger semantics. Preserve the untouched snapshot for audit; apply disabled schedule seeds separately.

External scheduling is independent of database schedule rows. Document the source-to-destination UID mapping privately, validate that the shared daily job handles both report times, and ensure only one sender can claim each report period. Preserve source history rather than clearing it to make migration easier.

Official guidance and its limits

Code Control explains source-code download and portability. Code export is a starting point; it does not itself recreate this application’s hosted services or external jobs.

Make a Copy currently applies to a user’s own projects. It copies code, database schema, and secrets, but not database rows; the copy starts unpublished. It is not a complete cross-account transfer workflow.

How to Restore Your Data describes official backup restoration with account-matching requirements. It is not a way to import another owner’s backup into an unrelated account. This custom transfer package is not an official Manus restoration package.
